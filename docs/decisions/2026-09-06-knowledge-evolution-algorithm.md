## 2. 备选方案与讨论理由

### 2.1 当场解决全部问题，或维护可跨轮保留的待验证列表

已选择维护待验证列表，在有限预算内分批验证。用户逐步确认了三种任务入口、调度次序、未决原因记录与有条件重试。

选择理由：Reference Planner 搜索和干预可能昂贵或暂时不可实施。允许问题跨轮保留，可以在继续交互的同时积累证据，不强迫系统把 UNKNOWN 解释为错误，也不要求清空所有问题后才继续运行。

代价：知识修正可能滞后，候选积累速度可能超过验证速度，调度可能使罕见或昂贵关系长期得不到验证。因此需要去重、照顾等待较久的问题、区分未决原因，并在系统性反证出现时及时撤下 confirmed 状态。

“每轮”是知识更新调度的单位，不固定为动作或 episode。重复经验可以只记录；新候选由新结构线索或有效冲突触发。没有新经验时，也可以继续处理已经积累的任务。

### 2.2 成本验证重新采样，或复用必要性验证的数据

讨论中最初提出为可用性比较重新建立配对世界，用户指出必要性验证已经具有可达性与参考时间数据。最终确认优先复用已有证据，只有数据不足或验证问题不同时追加验证。

硬机制与成本修饰是结论的不同类别，不要求两套独立证据。对照与消融都 FOUND 时，若已有参考时间保证足以支持差异判断，可以直接用于对应范围下的成本结论。

必须保留干预语义：全程禁止 A 与仅初始未拥有 A、后续允许获得 A，是不同条件。前者相对对照的时间差，不能直接当作“提前拥有 A 的收益”。

### 2.3 消融后可达立即删条件，或进一步区分解释

选择先记录证据，再区分冗余条件和 OR 替代机制。`A AND B -> Y` 在消融 A 后仍可达，不自动意味着 `B -> Y`；可能是同一世界中还有 C，使 `B AND C -> Y` 成立。

删除 A、建立替代机制、记录成本作用需要各自对应的证据。完整 Oracle 路径不能泄漏给学习端帮助发现 C；相关候选应来自公开规则、可观测经验及已有 Schema 上的局部搜索。

### 2.4 整批验证后更新，或每次有效证据到来即评估

选择立即评估。一次任务完成不代表整条关系已经验证完成，状态变化仍受证据标准约束。系统性反证成立时立即让 confirmed 回到 testing，后续复核可以排队。

修改关系时建立新候选并保留派生历史；提出新候选不自动废弃旧关系，确认覆盖旧范围的替代关系后才 supersede。这样避免在修正过程中丢失仍然有效的旧知识，也避免新候选未经验证就继承确认状态。

## 3. 最终决定与流程定位

以下为已确认事项的索引，具体行为以 PROJECT_BIBLE 第 7 节为准：

## 4. 完整示例：Crafter 制作木镐

### 4.1 示例性质与信息边界

本例已在讨论中逐步讲解并得到确认。交互记录、规划结果、状态推进和时间数值均为流程演示，不是已运行的实验，也不表示 Reference Planner 或干预 Adapter 已经实现。

讲解时于 2026-09-06 核对了 [Crafter 官方 data.yaml](https://github.com/danijar/crafter/blob/main/crafter/data.yaml) 中的规则：

```yaml
make:
  wood_pickaxe: {uses: {wood: 1}, nearby: [table], gives: 1}
```

该链接指向上游 main，不是固定实验版本。本次只用其核对示例配方；制作木镐消耗 1 个木材、要求附近有工作台，制作是一步原子动作。没有执行本地环境测试。

假设本例向学习端公开结构化库存与可判定的局部工作台邻近状态，但公开说明没有明确木材数量。精确底层配方是讲解者和验证端掌握的信息，不因本例列出源码而成为学习端的 declared_rule。LLM 关于数量的初始猜测标为 llm_prior，实际观测标为 empirical_transition。完整地图、全局坐标、底层配方表和规划器路径仍不对学习端开放。

如果某个实际环境配置已向玩家公开精确配方，则应使用该 declared_rule 生成候选，不应人为隐去已公开的信息来制造本例中的数量错误。

### 4.2 初始化：数量要求偏高的候选

审核后的 Schema 集合已包含：

```text
inventory_at_least(agent, item, quantity)
nearby(agent, object)
```

本例的 relation 标识为 M0、M1，不应与初始化公式中的整个候选集合 M_0 混淆。初始关系为：

```text
M0:
  P_start:
    inventory_at_least(agent, wood, 2)
    nearby(agent, table)
  P_hold: {}
  Y: inventory_at_least(agent, wood_pickaxe, 1)
  source: llm_prior
  epistemic_status: candidate
  lifecycle_status: current
```

M0 加入待验证列表，尚不能作为 confirmed 机制使用。节点仍然是参数化状态 Schema，`make_wood_pickaxe` 动作本身不是节点。

### 4.3 接收经验：成功但消耗量不足以证明前置阈值

Agent 在工作台旁成功制作木镐，可公开观测到：

| 库存 | 制作前 | 制作后 |
|---|---:|---:|
| wood | 2 | 1 |
| wood_pickaxe | 0 | 1 |

通过 RecordEvidence 保存状态变化与来源。该样本提供当前上下文中的可达证据，以及实际消耗 1 个木材的记录；不能仅凭消耗量就确认启动时只需 1 个木材，因为“消耗 1 个”与“启动至少有 1 个”是不同命题。

当前目标涉及木镐，因此 M0 按当前目标相关候选获得验证机会。若存在更高优先级的 confirmed 关系反证复核，则先调度后者。

### 4.4 对照：先确认当前条件下可达

基础世界中 Agent 存活、附近有工作台、初始 wood=2、wood_pickaxe=0。基础世界标识、环境范围、时间窗口和合法性条件随证据保存；其他可能影响判断的条件需在配对中保持可比。

复用上面的实际成功作为可达证据。为说明参考时间，假设验证端另外确认达到目标的最短路径为 1 步。Oracle 动作路径不传给学习端；学习端接收可达性、参考时间与相应保证。

### 4.5 单条件消融：禁止库存达到 2

对 `inventory_at_least(agent, wood, 2)` 执行必要性消融：

```text
初始 wood 从 2 改为 1；
整个验证窗口中要求 wood < 2；
其他条件保持可比。
```

这不是将木材清空。Adapter 必须验证赋值、约束与副作用；假设该配对合法且没有影响归因的混杂。验证端返回 FOUND，参考时间为 1 步。

| 条件 | 可达性 | 参考时间 |
|---|---|---:|
| 对照：初始 wood=2 | FOUND | 1 步 |
| 消融：初始 wood=1，整个窗口 wood<2 | FOUND | 1 步 |

本次结果表明，在所检验的世界与约束下，库存始终少于 2 仍可获得木镐。已有两组数据也未体现第 2 个木材的时间收益，可以直接复用，无须为了成本作用重复生成同样的配对。

这里只说明当前比较，没有外推为所有状态下都无成本作用，也未凭一次成功自动确认更小父条件。后续仍需检验更简单候选并排查替代解释。

### 4.6 Refine：在已有 Schema 内修正阈值

结合库存变化和消融证据提出：

```text
M1:
  P_start:
    inventory_at_least(agent, wood, 1)
    nearby(agent, table)
  P_hold: {}
  Y: inventory_at_least(agent, wood_pickaxe, 1)
  derived_from: M0
  epistemic_status: candidate
  lifecycle_status: current
```

M1 复用适用证据并进入验证。将数量参数从 2 改为 1 不新增 Schema，因此 V_t=V_0 仍成立。该公式固定的是节点表达种类，不是参数要求或关系。

### 4.7 补充验证与未决分支

在相应适用范围内继续收集证据。下表仅表示 Adapter 确认干预合法且无影响判断的混杂时，验证端可能返回的演示结果：

| 条件 | 演示结果 |
|---|---|
| 初始 wood=1，附近有工作台，wood_pickaxe=0 | FOUND，参考时间 1 步 |
| 整个窗口禁止拥有木材，目标初始未成立 | PROVEN_UNREACHABLE，限所检验窗口 |
| 整个窗口禁止处于工作台附近，目标初始未成立 | PROVEN_UNREACHABLE，限所检验窗口 |

邻近关系不能被默认视为可以无副作用地写入。改变位置、工作台或施加路径约束，均需 Adapter 检查；不能在最短路变化有混杂时仍直接归因于单个条件。若实际无法实现合格干预，则本项保留待验证，而不能假装已获得表中结果。

“全程不能靠近工作台就不可达”不证明 episode 起点必须在工作台旁。Agent 可以先移动过去；P_start 指制作机制启动时，制作是原子动作，因此 P_hold 为空。本例不用于验证复杂保持条件，也不将窗口内不可达当作无限时间不可达。

若搜索返回 UNKNOWN，记录预算不足等原因并保留任务；获得更多资源或新的合法验证条件后再处理。不在条件不变时反复执行相同搜索，也不将此记为 knowledge_gap。

### 4.8 状态更新与替代

每次有效新证据到来即评估 M1，但上述几个演示结果本身不规定确认所需样本量或范围覆盖。只有达到已确认的结构证据标准后，才令 M1 成为 confirmed。

假设后续证据足以确认 M1，且其适用范围能够覆盖 M0，则：

```text
M1: confirmed + current
M0: superseded
M0.replaced_by: M1
M1.derived_from: M0
```

M0 中“2 个木材足以制作”不一定是错误的充分性描述，但它没有给出更小的启动要求。将其作为多余限制被更准确关系替代时使用 superseded，不把整条充分性描述机械地判为 rejected。

旧证据、LLM 来源、状态变化和替代原因保留。如果新证据只支持更小适用范围的 M1，则不能替代整个 M0。M1 未确认前，也不能仅因提出修正候选就废弃 M0。

本例没有需要合并的独立等价关系，也没有退出维护的环境范围，因此不触发 Merge 或 Retire。完整算法不要求每个例子执行全部操作。

### 4.9 检索与本轮结束

正向检索在范围匹配时返回 current + confirmed 的 M1，表达“制作启动时有至少 1 个木材且附近有工作台，可获得木镐”。维护检索仍可读取 M0、LLM 原始候选、消融结果与派生历史。

预算耗尽或没有可执行任务时结束本轮，其余未决问题继续保留。当前 Agent 是否已经稳定掌握制作木镐的 Policy，不参与这条环境机制的结构判断。

该例实际演示的演化是：已有库存 Schema 的阈值由 2 修正为 1，伴随证据积累、状态更新与关系替代。它不包含在线新节点发现，也不演示尚未讨论完成的 Skill Library 调用协议。
